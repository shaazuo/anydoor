# 飞牛三方商店上架指引（更容易过审的技巧）

> 基于对飞牛官方上架规范、以及多个已上架三方应用（DeepSeek Harness、FnDepot、2FStore、FN软仓）的仓库调研整理。

## 一、先分清「上到哪个商店」

飞牛生态目前有两条路，审核严格程度完全不同：

| 渠道 | 审核 | 方式 | 适合 |
|---|---|---|---|
| **飞牛官方应用中心** | 严格，7 条硬规则 + 沙箱扫描 | 飞书表单提报 / 官方仓库 PR | 成熟、合规的应用 |
| **社区三方商店** | 宽松，规范自洽即可 | FN软仓 / FnDepot / 2FStore 提交 | 快速分发、保留扩展能力 |

**任意门目前走社区三方商店更合适**——它的核心能力（动态管理桌面快捷方式、反向代理、写 app_service 表）在官方审核眼里属于「高危行为」，大概率被拒。

## 二、社区商店统一的仓库规范（三个商店通用）

调研 FnDepot、2FStore、FN软仓后，发现它们对应用仓库的要求高度一致：

```
your-app-repo/
├── ICON.PNG          # 必须，全大写，64x64（2FStore 建议 256x256）
├── ICON_256.PNG      # 256x256 高清图标，优先使用
├── manifest          # 必须，应用清单
├── README.md         # 必须，介绍
└── .fpk             # Release 里的安装包（必须发布 Release）
```

### 关键字段口径

| 字段 | 要求 |
|---|---|
| `id` / `appname` | 仅小写字母、数字、连字符 |
| `display_name` | 应用显示名，**不得以「飞牛」为前缀** |
| `version` | **必须三段式**（如 `0.0.2`），四位式无效 |
| `ICON.PNG` | **文件名必须全大写**，否则客户端读不到 |
| 下载链接 | Release 里的 `.fpk`，或 raw 直链 |

## 三、飞牛官方 7 条规则对照（官方商店才需要，但建议都满足）

这是官方审核的核心红线，来自 `FNOSP/fnos-dsh` 的上架规范：

| # | 规则 | 说明 |
|---|---|---|
| 1 | **root 权限应用无法上架** | `config/privilege` 必须 `run-as: package`，不能用 root |
| 2 | **不监听公网端口** | 优先走统一网关，服务监听 `127.0.0.1`，manifest `checkport=false` |
| 3 | **platform 与真机验证** | 提交前必须在真实设备验证可安装可运行 |
| 4 | **文件读写校验路径安全** | 不能直接用用户传入的原始路径读写 |
| 5 | **付费内容首行声明** | 有付费须在介绍首行说明 |
| 6 | **版本号三段式** | 最容易踩的坑，四位式会走不到升级链路 |
| 7 | **名称不以「飞牛」为前缀** | `display_name` 不能用「飞牛」开头 |

## 四、更容易过审的实操技巧（调研结论）

### 1. 版本号三段式，且每次更新必升版本

飞牛应用中心按版本号判断是否安装，版本相同会被当同版本处理。**上架前必须确认 manifest 版本已提升**。

### 2. 图标文件名全大写

`ICON.PNG`（大写）是硬性要求，小写 `icon.png` 客户端读不到。建议同时提供 `ICON.PNG`（64）和 `ICON_256.PNG`（256）。

### 3. README 是门面

审核方和用户第一眼看 README。建议包含：这是什么、解决什么问题、功能列表、安装方式、截图、工作原理、注意事项。**截图很重要**——在真实 fnOS 设备的应用中心打开应用详情页截图。

### 4. 提供完整的 manifest 字段

`desc`（应用简介）、`changelog`（变更记录）、`maintainer`、`distributor`、`os_min_version` 都写清楚。描述要**具体说明用途**，首次上架说明应用用途，更新上架说明本次变更。

### 5. 发布 Release 而非只传代码

社区商店（尤其 2FStore/FnDepot）会自动从 GitHub Release 抓 `.fpk` 作为下载链接。所以必须：
- 打 tag（如 `v0.0.2`）
- 发布 Release（状态为「已发布」，非草稿）
- 把 `.fpk` 作为 Release 附件

### 6. 收敛 root 权限（重要）

即使是社区商店，`run-as: root` 也是明显的减分项/一票否决风险。能不用 root 就不用；必须用 root 时，在 README 里**明确说明为什么需要**，并强调「仅在受信任内网使用」。

### 7. 免责声明 + 合规声明

在 README 里写清楚：
- 本应用属于较底层操作，请仅在受信任内网使用
- 反向代理对象须是用户自己有权访问的服务
- 不含付费内容（或首行声明付费）

## 六、待决策项

1. **`run-as: root`**：任意门的核心能力（`appcenter-cli`、写 `app_service` 表、动态装卸载应用）本质上需要 root。改 `package` 会直接跑不起来。这是「能力」与「合规」的真实冲突，需要权衡。
2. **监听地址**：管理端监听 `0.0.0.0`（所有网卡），转发器同理。可考虑收敛到内网网卡。
